# Release Changelogs

This directory contains automatically generated changelogs for each release of ThemisDB.

## Overview

When a new version tag is pushed (e.g., `v1.3.1`, `v1.4.0`), the release build workflow automatically:

1. Analyzes all commits since the previous release
2. Identifies changed files and their types
3. Categorizes changes (features, bug fixes, documentation, refactoring)
4. Generates a detailed changelog document
5. Commits the changelog to this directory

## Changelog Format

Each changelog file is named `RELEASE_CHANGELOG_vX.Y.Z.md` and contains:

- **Release metadata**: Date, time, version, previous version
- **Commits**: Complete list of all commits with authors
- **Changed files**: Collapsible list of modified files with change types
- **File statistics**: Count of changed files by type (C++, Python, Markdown, YAML, JS/TS)
- **Change categories**: Count of features, bug fixes, documentation, and refactoring commits
- **Docker images**: Available Docker image tags and pull commands

## Usage

### View Latest Release Changelog

```bash
# View the most recent release changelog
ls -t release-changelogs/ | head -1 | xargs -I {} cat release-changelogs/{}
```

### Find Changes for Specific Version

```bash
# View changelog for a specific version
cat release-changelogs/RELEASE_CHANGELOG_v1.3.0.md
```

### List All Releases

```bash
# List all release changelog files
ls -1 release-changelogs/
```

## Automated Generation

The changelogs are automatically generated by the GitHub Actions workflow `.github/workflows/release-build.yml` in the `generate-changelog` job.

The generation process:
1. Uses `git log` and `git diff` to collect all changes since the previous tag
2. Analyzes commit messages for categorization
3. Counts changed files by type
4. Formats everything into a structured Markdown document
5. Commits the changelog back to the repository

## Retention

- Changelog files are kept in the repository indefinitely
- They are also uploaded as workflow artifacts with 90-day retention
- Each file is approximately 5-50 KB in size depending on release scope

## Integration with Main Changelog

These release changelogs are separate from the main `CHANGELOG.md` file at the repository root, which follows [Keep a Changelog](https://keepachangelog.com/) format and documents releases manually with curated content.

The automated release changelogs provide complete, machine-generated documentation of all changes between versions.

## Difference from Nightly Changelogs

Previously, the project used nightly changelogs that documented daily changes. The new release-based approach:

- **Triggers**: On version tags instead of daily schedule
- **Scope**: Documents all changes between releases instead of last 24 hours
- **Location**: `release-changelogs/` instead of `nightly-changelogs/`
- **Purpose**: Release documentation instead of development tracking

## Troubleshooting

If a release build is triggered but no changelog is generated, check:
1. The workflow logs in the Actions tab
2. Git configuration and push permissions
3. Whether there were any commits since the previous tag

To manually trigger a changelog generation, use the workflow_dispatch trigger with the version parameter.
