# Config Module Trust Model

## Scope and trust boundaries

This document is for developers and operators handling config-module data.
`src/config` consumes filesystem paths, config/schema content, environment
selection, filesystem events, and encrypted-store snapshots supplied by
callers or the deployment. Treat all of these as untrusted until validated.
The module does not establish caller identity or authorization; those controls
belong to the service and deployment boundaries that invoke it.

## Risks and controls

| Risk | Control and residual boundary |
|---|---|
| Path traversal, invalid bytes, overlong paths, or missing mappings | Resolver normalization and validation; hardening tests cover traversal, NUL, size, and fallback cases. A failed resolution must not be interpreted as success. |
| Malformed or adversarial config/schema input | JSON/YAML parsing, schema diagnostics, contract size/depth limits, and document-local `$ref` handling. External references are not fetched. Unsupported keywords are not an enforcement mechanism. |
| Secret exposure through logs or audit | Do not log plaintext values. Audit entries retain requested/resolved paths and can expose filesystem layout; enable and export them deliberately. |
| Ciphertext modification or malformed encryption metadata | AES-256-GCM authentication and explicit decryption errors; IV/tag lengths are validated. Treat authentication failure as an integrity signal. |
| Serialized-store disclosure | `serialize()` includes the current key bytes, encoded as base64. Protect the entire snapshot as key material; base64 does not encrypt it. |
| Denial or resource exhaustion through large/churning inputs | Apply the frozen contract's path/file/schema/key/value/count/depth bounds and watcher timing limits; monitor misses, fallbacks, and watcher diagnostics. |

## Key and access handling

The encrypted store is an in-memory component with a key generated by the
implementation; it is not an external KMS or a deployment secret-management
service. Keep access to the process and serialized snapshots restricted.
Rotation re-encrypts current entries and replaces the key; it does not create an
external backup or key escrow. Applications remain responsible for transport,
authorization, durable secret protection, and deployment-specific key policy.

## Incident handling

For suspected path abuse, secret leakage, snapshot exposure, or ciphertext
tampering: preserve relevant logs and a restricted copy of the artifact,
prevent further unsafe reads/writes, notify the owning service's incident lead,
and follow the project-level `SECURITY.md` reporting process. Do not include
plaintext secrets or unredacted serialized snapshots in an issue, chat, or
general-purpose log. See [`RUNBOOK.md`](RUNBOOK.md) for operational triage and
[`../../include/config/config_contract.h`](../../include/config/config_contract.h)
for the frozen v1.x control contract.
