# Embedding Plugin Boundary

## Purpose and scope

This page is for developers integrating image-analysis backends that expose
embedding methods. It distinguishes interface support from an implemented model:
`src/plugins` contains runtime and lifecycle infrastructure, not an embedding
model implementation or a semantic-quality evaluation suite.

## Available interface

`PluginType::EMBEDDING` is a category in
[`plugin_interface.h`](../../include/plugins/plugin_interface.h). Separately,
[`image_analysis_interface.h`](../../include/plugins/image_analysis_interface.h)
declares `IImageAnalysisBackend::generateEmbedding()` and
`generateTextEmbedding()`. Its `EmbeddingResult` contains:

- `success` and `error_message`;
- a `std::vector<float>` and declared `dimension`;
- `model_name`; and
- `inference_time_ms`.

The enum category and image-analysis interface are separate surfaces: the
generic `IThemisPlugin` API does not define a dedicated `IEmbeddingPlugin`
interface, and the image interface has its own entry-point macro. Neither
declaration proves that a backend is wired into the generic manager.

The interface does not define a universal vector dimension, normalization
scheme, distance metric, tokenizer, or model-version compatibility rule.
Consumers must verify those properties against the selected backend and the
index/query contract. An image-plugin category does not by itself guarantee
that a plugin supports embeddings: `YOLOv8OnnxPlugin` explicitly documents
`generateEmbedding()` as unsupported.

## Integration invariants

1. Check the backend's declared capability and `EmbeddingResult::success`;
   do not interpret a failed result as an empty but valid vector.
2. Validate the returned dimension and finite values before indexing.
3. Keep model identity/version and preprocessing consistent between indexed
   content and query generation. Cross-model vectors are not assumed
   comparable by this interface.
4. Treat batch behavior as backend-specific. The image interface's default
   `generateEmbeddingBatch()` loops over individual calls, and its default
   `generateTextEmbedding()` returns an unsupported result; neither promises
   parallel inference or a throughput improvement.
5. Account for backend memory, device selection, and concurrency rules during
   initialization and shutdown. Those are implementation properties, not
   guarantees of the generic plugin loader.

## Evaluation and reproducibility

The core plugin module has no embedding-quality benchmark or expected
dimension. A backend evaluation should record its exact model artifact and
version, preprocessing, output dimension, normalization, hardware/runtime,
latency distribution, failure count, and task-level retrieval metric on a
fixed dataset. Compare query and indexed-document embeddings generated by the
same compatible model configuration. These measurements belong with the
backend or consuming retrieval module; they must not be presented as measured
results of `src/plugins`.

The plugin runtime's lifecycle and registry tests validate loading and
interface wiring, not semantic quality. Use the focused plugin tests listed in
[`MODELING.md`](./MODELING.md) for runtime contracts and backend-specific tests
for inference behavior.

## Source boundary

Relevant declarations are in
[`plugin_interface.h`](../../include/plugins/plugin_interface.h),
[`image_analysis_interface.h`](../../include/plugins/image_analysis_interface.h),
and [`yolov8_onnx_plugin.h`](../../include/plugins/yolov8_onnx_plugin.h).
There is no corresponding embedding implementation in the current
`src/plugins` source set. Keep model selection, training, vector quality, and
retrieval metrics in their owning backend or retrieval module documentation.

See [`RESEARCH.md`](./RESEARCH.md) for evaluation of runtime choices and
[`API.md`](./API.md) for the plugin-loading contracts.
