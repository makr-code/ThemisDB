# ONNX CLIP Research Notes

Exact model backend not verifiable from final document text alone.

## Purpose and evidence boundary

This page records what the current `onnx_clip` implementation demonstrates and
what would need independent evaluation before it could support claims about CLIP
quality. It is for maintainers deciding whether to integrate or extend the
backend. The implementation in [`onnx_clip_plugin.cpp`](./onnx_clip_plugin.cpp)
and focused tests under [`tests/onnx_clip/`](../../tests/onnx_clip/) are the
primary evidence; test names and historical phase reports are not proof of
inference with pretrained model assets.

## Research question and current assumption

The module exposes image and text embedding methods through
`IImageAnalysisBackend`. The key research question is whether outputs preserve
the semantic image/text relationships required for similarity search.

The current source does not answer that question: image bytes and normalized
text-derived hashes seed a deterministic pseudo-random vector generator. It
does not decode image pixels, execute an ONNX graph, load CLIP weights, or map
text and image inputs into a learned shared space. `model.name` is a result label;
it does not select or load a pretrained model. Therefore this backend is a
contract/reference implementation, not evidence of CLIP model quality.

## Method and evidence

- Image path: a 64-bit FNV-1a-style hash over the supplied bytes, using the
  source's initial constant, optionally mixed with width, height, channel count,
  and bit depth from `ImageMetadata`; xorshift64* then generates the configured
  number of components, which are L2-normalized.
- Text path: lowercases characters and splits on whitespace and punctuation,
  combines 64-bit FNV-1a-style hashes of the original text and tokens, then
  generates and normalizes a vector. This is not CLIP BPE tokenization.
- Existing focused tests use deterministic generated byte arrays and mock
  model files. They check properties such as dimensionality, normalization,
  repeatability, batching, and lifecycle behavior. They do not measure semantic
  retrieval quality against a labeled dataset or pretrained CLIP vectors.

## Evaluation required for a real model

Before describing this module as semantic CLIP inference, add model-backed
evidence that is reproducible and records the model artifact digest, tokenizer,
preprocessing implementation, runtime/provider version, and test data version.
At minimum evaluate:

1. Image-to-text and text-to-image retrieval on a fixed, licensed benchmark.
2. Recall@K or another predeclared retrieval metric, reported separately by
   model variant and input modality.
3. Image and text embedding dimensions, finite values, and L2 norms; compare
   vectors with a reference implementation using an explicitly stated
   tolerance.
4. Repeatability across clean processes and supported execution providers.
5. Latency percentiles, throughput, and peak resident memory for single inputs
   and configured batch sizes.

Store benchmark inputs or stable dataset identifiers, commands, environment,
and results with the test evidence. Do not treat generated-vector tests as
substitutes for this evaluation.

## Trade-offs and limits

The deterministic path is useful for exercising interface contracts without
shipping model assets or requiring a provider at test time. Its low runtime
cost and reproducibility do not imply useful nearest-neighbor semantics. It
must not be used to claim model accuracy, cross-modal compatibility, or
production retrieval quality.
