## 1. Overview

### Purpose
Define key lifecycle semantics for ThemisDB's cryptographic key material. This document establishes contracts for all modules that generate, store, use, or rotate keys.

### Scope
- All cryptographic key material management in ThemisDB
- Key derivation (HKDF)
- Key storage and encryption (LEK, KEK)
- Key rotation and versioning
- Key revocation and expiration
- Audit trail requirements

### Canonical References
- **RFC 5869**: HKDF Key Derivation Function
- **NIST SP 800-38D**: AES-GCM (Galois/Counter Mode)
- **SECURITY.md**: ThemisDB security policy and incident response

## 2. Key Lifecycle Phases

### Phase 1: Generation

**Purpose:** Create new key material securely

**Mechanism:**
```
Random Entropy → HKDF-SHA256 → Cryptographic Key
    (or master key input)
```

**Requirements:**
- Use cryptographically strong randomness (OpenSSL RAND)
- Minimum 256 bits of entropy for AES-256
- Use HKDF for deterministic derivation (not raw random)
- Never reuse same IKM+salt+info tuple

**Contracts:**
- HKDF minimum IKM size: 16 bytes (recommended: 32+ bytes)
- HKDF minimum salt size: 16 bytes (if provided)
- Output length: 1-8160 bytes (per RFC 5869 SHA-256 limit)

**Example:**
```cpp
// LEK generation (daily)
auto lek = HKDFHelper::derive(
    random_entropy,        // 256-bit random
    domain_salt,           // Per-domain salt
    "log.encryption.v1",   // Domain-specific context
    32                     // AES-256 key
);
```

**Audit Trail:**
- KEY_GENERATED event with key_id, algorithm, size
- Timestamp and generating module
- Reason (rotation, incident, etc.)

### Phase 2: Storage

**Purpose:** Persist keys securely with encryption

**Mechanisms:**
```
┌─────────────────────────────────────┐
│  Unencrypted Key (in Memory)        │
└──────────────┬──────────────────────┘
               │ Encrypt with KEK
               ↓
┌─────────────────────────────────────┐
│  Encrypted Key Blob (in RocksDB)    │
│  Format: lek:encrypted:<date>       │
│  = AES-GCM(KEK, LEK, associated_ad) │
└─────────────────────────────────────┘
```

**Requirements:**
- All keys must be encrypted before persistent storage
- Use AES-GCM with authenticated encryption (no separate MAC)
- Include associated data (AAD) for integrity
- KEK must be stored securely (derived from PKI cert)

**Storage Contract:**
- RocksDB key: `lek:encrypted:<YYYY-MM-DD>`
- RocksDB value: AES-GCM(KEK, LEK, AAD)
- AAD includes: key_id, algorithm, timestamp
- Cipher: AES-256-GCM (256-bit key, 96-bit IV)

**Example:**
```cpp
// Storage in RocksDB
std::string db_key = "lek:encrypted:2026-08-08";
std::vector<uint8_t> encrypted_lek = AES_GCM_encrypt(
    kek,              // Key Encryption Key
    lek,              // Log Encryption Key to encrypt
    nullptr, 0,       // IV (generated by OpenSSL)
    (const uint8_t*)"lek:2026-08-08", 15  // AAD
);
db->Put(db_key, encrypted_lek);
```

**Audit Trail:**
- KEY_STORED event with key_id, storage_location
- Encryption algorithm, key size
- Encryption timestamp

### Phase 3: Usage

**Purpose:** Apply keys to encrypt/decrypt data

**Contracts:**
- Only use non-revoked keys
- Only use non-expired keys for new encryption
- Expired keys may be used for decryption (backward compatibility)
- Track key usage for audit purposes

**Revocation Check:**
```cpp
bool can_use(const std::string& key_id) {
    return !is_revoked(key_id) && !is_expired(key_id);
}

// For decryption (backward compatibility)
bool can_decrypt(const std::string& key_id) {
    return !is_revoked(key_id);  // Can decrypt even if expired
}
```

**Usage Patterns:**

**New Encryption (Use Current Key):**
```cpp
std::string current_lek = lek_manager->getCurrentLEK();
if (can_use(current_lek)) {
    encrypted_data = encrypt(data, current_lek);
}
```

**Decryption (Try Multiple Versions):**
```cpp
// Try current key first
auto decrypted = decrypt(data, current_key);
if (decrypted.empty()) {
    // Fall back to yesterday's key
    auto old_key = lek_manager->getLEKForDate(yesterday);
    if (can_decrypt(old_key)) {
        decrypted = decrypt(data, old_key);
    }
}
```

**Audit Trail:**
- KEY_USED event with key_id, operation (encrypt/decrypt)
- Data size, timestamp, module
- Success/failure status

### Phase 4: Rotation

**Purpose:** Replace keys periodically to limit impact of compromise

**Strategy:**
- **LEK (Log Encryption Key)**: Daily rotation at UTC midnight
- **KEK (Key Encryption Key)**: Annual or incident-driven rotation
- **Master Keys**: Annual rotation (certificate-based)

**Rotation Mechanism:**
```
Current Key (2026-08-07)
         │
         │ [Automatic at midnight UTC]
         ↓
New Key Created (2026-08-08)
         │
         ├─ Store encrypted in RocksDB
         ├─ Update cache with new key_id
         └─ Emit KEY_ROTATED audit event
         
Old Key (2026-08-07)
         │
         ├─ Still available for decryption
         ├─ Marked for revocation after max_age_days
         └─ Eventually purged from cache
```

**Rotation Configuration:**
```cpp
lek_manager->startAutoRotation(
    std::chrono::seconds(3600),   // Check every hour
    30                            // Revoke keys older than 30 days
);
```

**Manual Rotation (Incident Response):**
```cpp
// Force immediate rotation
lek_manager->rotate();

// Verify new key created
std::string new_lek = lek_manager->getCurrentLEK();
LOG(INFO) << "New LEK: " << new_lek;
```

**Audit Trail:**
- KEY_ROTATED event
- Old key_id and new key_id
- Rotation reason (automatic/manual)
- Timestamp
- New key parameters (algorithm, size)

### Phase 5: Revocation

**Purpose:** Prevent key use in response to compromise or policy

**Triggers:**
- Security incident: key compromise detected
- Compliance: regulatory requirement
- Policy: forced rotation after max_age_days
- Audit: administrative decision

**Revocation Mechanism:**
```
Key marked as revoked
         │
         ├─ Stored in RocksDB: lek_revoked:<key_id>
         ├─ Added to in-memory revocation list
         ├─ Checked on every decryption attempt
         └─ Permanent (cannot unrevoke)
```

**Revocation API:**
```cpp
// Revoke a key
bool revoked = lek_manager->revokeKey("2026-08-05");

// Check revocation status
bool is_revoked = lek_manager->isRevoked("2026-08-05");

// Get all revoked keys
auto revoked_list = lek_manager->getRevokedKeys();
```

**Revocation Guarantees:**
- Revoked key: Cannot be used for any operation
- Revocation is permanent during process lifetime
- Revocation persists across restarts (RocksDB storage)
- Revocation affects all readers/decryption attempts

**Audit Trail:**
- KEY_REVOKED event
- Reason for revocation
- Revoking user/module
- Timestamp
- Associated incident ID (if applicable)

### Phase 6: Destruction

**Purpose:** Ensure key material is unrecoverable after lifecycle ends

**Destruction Mechanisms:**

**Memory:**
```cpp
// Explicit cleanup (for sensitive operations)
OPENSSL_cleanse(key.data(), key.size());

// In-cache cleanup (automatic)
// ├─ OPENSSL_cleanse when evicted from shard
// └─ Automatic after TTL expiration
```

**Storage:**
```cpp
// Logical deletion (key still in DB, marked as revoked)
lek_manager->revokeKey(key_id);

// Physical deletion (not currently implemented; may add)
// db->Delete("lek:encrypted:" + key_id);
```

**Design Note:** Keys are NOT physically deleted from storage to support:
- Audit trail reconstruction
- Decryption of historical data
- Compliance retention requirements

**Cleanup Responsibility:**
- **Cache eviction**: Framework handles (HKDF cache)
- **Explicit cleanup**: Application responsible (use OPENSSL_cleanse)
- **Persistence cleanup**: Database admin responsible (RocksDB compaction)

## 3. Key Contracts

### 3.1 HKDF (HMAC-based Key Derivation Function)

**Specification:** RFC 5869  
**Hash Algorithm:** SHA-256  
**Output Limit:** 255 * 32 = 8160 bytes

**Input Contract:**
```
Inputs (all required):
├─ IKM (Input Key Material): 16-256 bytes
│   └─ Cryptographically strong secret
├─ Salt: 0-256 bytes (16+ bytes recommended)
│   └─ Randomization, empty OK but less secure
├─ Info: 0-256 bytes (context string)
│   └─ Domain separation, empty OK
└─ Length: 1-8160 bytes
    └─ Output size in bytes
```

**Output Contract:**
```
Outputs (deterministic):
└─ OKM (Output Key Material): exactly Length bytes
    ├─ Indistinguishable from random to attacker
    ├─ Non-invertible (cannot recover IKM)
    └─ Domain-separated by Info string
```

**Security Properties:**
- **Deterministic:** Same inputs → same output
- **Pseudo-Random:** Output ≈ random (indistinguishable)
- **Non-Invertible:** OKM → IKM is computationally infeasible
- **Domain Separation:** Different info → different keys

**Example Contracts:**

```cpp
// Contract: Session key derivation
Inputs:
  IKM = master_key (32 bytes, from secure storage)
  Salt = session_id (random per request)
  Info = "auth.session.v1"
  Length = 32

Output:
  Session key (32 bytes, unique per session)
  Can decrypt only data encrypted with same session_id
```

```cpp
// Contract: Multi-purpose key derivation
Inputs:
  IKM = root_key (common across all purposes)
  Salt = empty or constant (same for all)
  Info = "purpose.v1" (different per purpose)
  Length = 32

Outputs:
  Different keys for different purposes
  Cannot cross-decrypt between purposes
```

### 3.2 LEK (Log Encryption Key)

**Lifecycle:** Daily  
**Algorithm:** AES-256-GCM  
**Size:** 256 bits (32 bytes)

**Generation Contract:**
```
LEK = RAND(256 bits) or HKDF(...)
  └─ One per calendar day (YYYY-MM-DD)
  └─ Created at UTC midnight or on-demand
```

**Storage Contract:**
```
Encrypted LEK = AES-GCM(KEK, LEK, AAD)
  where AAD = "lek:encrypted:<YYYY-MM-DD>"
  
RocksDB Entry:
  Key: "lek:encrypted:2026-08-08"
  Value: [AES-GCM encrypted LEK blob]
```

**Revocation Contract:**
```
Revoked LEK:
  RocksDB Entry:
    Key: "lek_revoked:2026-08-08"
    Value: [timestamp, reason]
    
  In-Memory: revoked_keys_.insert("2026-08-08")
  
  Guarantee: Cannot decrypt with revoked key
```

**Expiration Contract:**
```
Expired LEK = created more than max_age_days ago
  └─ Default: 30 days
  └─ Can decrypt (backward compatibility)
  └─ Cannot encrypt (policy enforced)
```

**Audit Trail Contract:**
```
KEY_ROTATED:
  │
  ├─ Event: "KEY_ROTATED"
  ├─ old_key_id: "lek_2026-08-07"
  ├─ new_key_id: "lek_2026-08-08"
  ├─ reason: "automatic" | "manual" | "incident"
  ├─ timestamp: ISO 8601
  └─ module: "lek_manager"

KEY_REVOKED:
  │
  ├─ Event: "KEY_REVOKED"
  ├─ key_id: "lek_2026-08-08"
  ├─ reason: "compromise" | "policy" | "incident"
  ├─ timestamp: ISO 8601
  └─ incident_id: (optional)
```

### 3.3 KEK (Key Encryption Key)

**Lifecycle:** Annual or incident-driven  
**Algorithm:** AES-256 (derived from PKI)  
**Derivation:** HKDF-SHA256 from certificate

**Generation Contract:**
```
KEK = HKDF(
  IKM = PKI certificate material
  Salt = service-specific constant
  Info = "lek-kek.v1"
  Length = 32 bytes
)
```

**Storage Contract:**
```
KEK is NOT stored explicitly
  └─ Derived on-demand from PKI certificate
  └─ Each process derives identical KEK
  └─ Ensures consistency across replicas
```

**Rotation Contract:**
```
KEK Rotation (annual):
  1. New KEK derived from new certificate
  2. All LEKs must be re-encrypted with new KEK
  3. Old KEK retained briefly for decryption
  4. Old LEKs gradually purged
  
  Timeline:
    Day 0: New certificate issued → new KEK derived
    Day 1-7: Support both old and new KEK for decryption
    Day 8+: Use only new KEK
```

## 4. Integration Points

### 4.1 Auth Module

**Key Usage:**
- **Session keys:** LEK for encrypting session tokens
- **Token keys:** HKDF for deriving token signing keys
- **Password hashing:** HKDF for key stretching

**Integration Pattern:**
```cpp
// Session encryption
auto session_key = hkdf_cache.derive_cached(
    master_key,
    session_id_salt,
    "auth.session.v1",
    32
);

// Token signing
auto token_key = hkdf_cache.derive_cached(
    master_key,
    token_id_salt,
    "auth.token.v1",
    32
);
```

**Audit Requirements:**
- Track which keys encrypt which sessions
- Log key rotation affecting active sessions
- Monitor key derivation rate

### 4.2 Process Module

**Key Usage:**
- **Process encryption:** LEK for encrypted process data
- **Communication keys:** HKDF for inter-process encryption

**Integration Pattern:**
```cpp
// Encrypt process state
std::string process_lek = lek_manager->getCurrentLEK();
encrypted_state = encrypt_with_lek(process_data, process_lek);

// Decrypt on retrieval
decrypted_state = decrypt_with_lek(encrypted_state, process_lek);
```

**Audit Requirements:**
- Track processes encrypted with each LEK
- Log re-encryption after key rotation
- Monitor key usage by process type

### 4.3 Storage Module

**Key Usage:**
- **At-rest encryption:** LEK for encrypting stored data
- **Backup encryption:** Different key per backup

**Integration Pattern:**
```cpp
// Store with current LEK
std::string storage_lek = lek_manager->getCurrentLEK();
encrypted_record = encrypt_record(record, storage_lek);
db->put(encrypted_record);

// Retrieve with appropriate LEK
std::string record_lek = getLEKForDate(record_date);
decrypted_record = decrypt_record(encrypted_record, record_lek);
```

**Audit Requirements:**
- Track storage records by encryption key
- Monitor decryption requests for historical data
- Alert on attempts to decrypt with revoked key

### 4.4 Query Module

**Key Usage:**
- **Query result encryption:** LEK for result sets
- **Index encryption:** HKDF for encrypted index keys

**Integration Pattern:**
```cpp
// Encrypt query results
std::string result_lek = lek_manager->getCurrentLEK();
encrypted_results = encrypt_results(results, result_lek);

// Decrypt for consumer
decrypted_results = decrypt_results(encrypted_results, result_lek);
```

**Audit Requirements:**
- Log decryption of query results
- Monitor key usage by query type
- Alert on suspicious decryption patterns

## 5. Security Considerations

### 5.1 Threat Model

**Threat: Key Extraction from Memory**
```
Attack: Cold boot, memory dump, or debugger
Mitigation: OPENSSL_cleanse on eviction
Mitigation: OS-level memory protection (mlock, SecureString)
Residual Risk: Cannot prevent privileged process access
```

**Threat: Key Extraction from Storage**
```
Attack: Direct database access, disk recovery
Mitigation: Encrypt LEKs with KEK before storage
Mitigation: KEK derived from PKI certificate (not stored)
Residual Risk: Database corruption could expose plaintext
```

**Threat: Replay Attacks**
```
Attack: Replay old encrypted data with old key
Mitigation: Timestamp checks in audit trail
Mitigation: Key expiration after max_age_days
Residual Risk: Expired keys still decrypt old data
```

**Threat: Timing Attacks**
```
Attack: Measure key derivation time to infer key properties
Mitigation: HKDF is constant-time (per RFC 5869)
Mitigation: Cache timing depends on entry age, not key value
Residual Risk: Cache hit/miss observable from timing
```

**Threat: KEK Compromise**
```
Attack: KEK extracted; all LEKs decryptable
Impact: All encrypted data compromisable
Mitigation: LEK rotation limits damage window (1 day)
Mitigation: Incident response: rotate KEK + re-encrypt LEKs
```

**Threat: LEK Compromise**
```
Attack: LEK extracted; one day's data decryptable
Impact: One calendar day's data compromised
Mitigation: LEK rotation limits exposure to single day
Mitigation: Incident response: revoke + rotate immediately
```

### 5.2 Mitigations

| Threat | Mitigation | Responsibility |
|--------|-----------|-----------------|
| Memory extraction | OPENSSL_cleanse() | Application |
| Storage extraction | LEK encryption with KEK | Framework |
| Timing attacks | Constant-time HKDF | OpenSSL |
| Replay attacks | Key expiration | Framework |
| KEK compromise | Annual rotation | Admin |
| LEK compromise | Daily rotation + revocation | Framework |
| Unauthorized access | RBAC + audit logging | Application |
| Accidental exposure | Secure cleanup on error | Application |

### 5.3 Audit Trail Requirements

**Mandatory Events:**

```
KEY_GENERATED:
  - key_id, algorithm, size
  - timestamp, module
  - reason (rotation, incident, etc.)
  
KEY_USED:
  - key_id, operation (encrypt/decrypt)
  - data_size, timestamp, module
  - success/failure
  
KEY_ROTATED:
  - old_key_id, new_key_id
  - reason, timestamp
  - auto/manual/incident
  
KEY_REVOKED:
  - key_id, reason
  - revoking_user, timestamp
  - incident_id (if applicable)
  
KEY_EXPIRED:
  - key_id, age_days
  - timestamp, module
  - action_taken
```

**Monitoring:**
- Alert on unexpected revocations
- Alert on failed decryptions with revoked key
- Alert on key derivation rate anomalies
- Daily report of key rotation events
- Quarterly audit of revocation reasons

## 6. Implementation Guide

### 6.1 RAII Patterns for Key Handles

```cpp
// Bad: Manual cleanup (easy to forget)
{
    auto key = cache.derive_cached(...);
    use_key(key);
    OPENSSL_cleanse(key.data(), key.size());  // Must remember!
}

// Good: RAII wrapper
class KeyHandle {
public:
    KeyHandle(const std::vector<uint8_t>& key) : key_(key) {}
    ~KeyHandle() { OPENSSL_cleanse(key_.data(), key_.size()); }
    
    const std::vector<uint8_t>& data() const { return key_; }
    
private:
    std::vector<uint8_t> key_;
};

{
    KeyHandle key(cache.derive_cached(...));
    use_key(key.data());
}  // Automatically cleaned
```

### 6.2 Memory Zeroing

**Approach 1: OPENSSL_cleanse (Recommended)**
```cpp
std::vector<uint8_t> key = /* ... */;
OPENSSL_cleanse(key.data(), key.size());
```

**Approach 2: volatile_free (Alternative)**
```cpp
uint8_t* key = /* allocated */;
volatile_free(key, key_size);
```

**Approach 3: Manual Volatile (Last Resort)**
```cpp
volatile uint8_t* key_ptr = (volatile uint8_t*)key.data();
for (size_t i = 0; i < key.size(); ++i) {
    key_ptr[i] = 0;
}
```

### 6.3 Thread-Safe Key Storage

```cpp
// Bad: Global unprotected access
std::vector<uint8_t> master_key = /* ... */;  // Race condition!

// Good: Thread-local or protected storage
class KeyStorage {
public:
    std::vector<uint8_t> get_master_key() const {
        std::lock_guard<std::mutex> lock(mu_);
        return master_key_;
    }
    
private:
    mutable std::mutex mu_;
    std::vector<uint8_t> master_key_;
};

// Or use thread-local HKDF cache
auto& cache = HKDFCache::threadLocal();
auto key = cache.derive_cached(...);
```

### 6.4 Error Handling and Fallback

```cpp
// Comprehensive error handling
std::string decrypt_or_fallback(
    const std::string& encrypted_data,
    const std::string& expected_date) {
    
    try {
        // Try current key first
        auto lek = lek_manager_->getCurrentLEK();
        auto decrypted = decrypt(encrypted_data, lek);
        if (!decrypted.empty()) return decrypted;
        
        // Fall back to expected date
        if (!expected_date.empty()) {
            auto old_lek = lek_manager_->getLEKForDate(expected_date);
            if (!old_lek.empty()) {
                decrypted = decrypt(encrypted_data, old_lek);
                if (!decrypted.empty()) return decrypted;
            }
        }
        
        // Fall back to previous day
        auto prev_date = get_previous_date(lek_manager_->getCurrentDateString());
        auto prev_lek = lek_manager_->getLEKForDate(prev_date);
        if (!prev_lek.empty()) {
            return decrypt(encrypted_data, prev_lek);
        }
        
    } catch (const std::exception& e) {
        LOG(ERROR) << "Decryption error: " << e.what();
    }
    
    return "";  // All attempts failed
}
```
