# LLM Module — Canonical Metrics Schema

**Status:** Implemented ✅ (metrics wired in `src/llm/grafana_metrics.cpp`, alerting rules active in `prometheus/rules/llm_alerts.yml`, dashboard validated in `grafana/dashboards/themisdb-llm-dashboard.json`)
**Version:** 1.5.0
**Last Updated:** April 2026

---

## Purpose

This document defines the **canonical set of Prometheus metric names, labels, units, and collection points** for the ThemisDB LLM module (`src/llm`). All implementation work (wiring metrics into the hot path, defining Grafana dashboard panels, writing alerting rules) **must reference this schema**. Renaming metrics after release breaks dashboards, alerts, and saved PromQL queries.

See `prometheus/rules/llm_alerts.yml` for alerting rules that consume these metrics.

---

## Conventions

| Convention | Choice | Rationale |
|------------|--------|-----------|
| Time unit | **seconds** (suffix `_seconds`) | Prometheus standard; use `_ms` suffix only for histograms where millisecond buckets are needed for precision (see note below) |
| Size unit | **bytes** (suffix `_bytes`) | Prometheus standard |
| Counter suffix | `_total` | Required by Prometheus exposition format for counters |
| Histogram suffix | `_bucket`, `_sum`, `_count` | Auto-generated by Prometheus client libraries |
| Label naming | `snake_case` | Consistent with Prometheus community conventions |
| Namespace | `llm_` | Scopes all LLM metrics; avoids collision with sharding/storage metrics |

> **Note on milliseconds vs seconds:** The existing `grafana_metrics.cpp` implementation uses `_ms` suffixes (e.g., `llm_inference_duration_ms`). Migrating to `_seconds` is recommended but is a **breaking change** for any deployed dashboards. The schema below preserves the current `_ms` suffix for histograms to avoid breaking existing integrations; new metrics added going forward should use `_seconds`.

## 1. Inference Metrics

### `llm_inference_requests_total` (Counter)

Total number of inference requests received.

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | e.g. `llama-3.2-1b-q8_0` | Identifier of the model serving the request |

**Collection point:** `LlamaWrapper::generate()` entry.

---

### `llm_inference_failures_total` (Counter)

Total number of inference requests that ended in an error.

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | — | Model that produced the failure |
| `error` | string | `timeout`, `oom`, `invalid_input`, `grammar_error`, `internal` | Error category |

**Collection point:** `LlamaWrapper::generate()` error path; `ContinuousBatchScheduler` rejection path.

---

### `llm_inference_duration_ms` (Histogram)

End-to-end inference duration in milliseconds (from request receipt to last token).

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | — | Serving model |

**Suggested buckets (ms):** `[50, 100, 250, 500, 1000, 2500, 5000, 10000, 30000]`

**Collection point:** `LlamaWrapper::generate()` — measure from entry to completion.

---

### `llm_first_token_latency_ms` (Histogram)

Time from request receipt to emission of the first output token (TTFT), in milliseconds.

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | — | Serving model |

**Suggested buckets (ms):** `[10, 25, 50, 100, 250, 500, 1000, 2500, 5000]`

**Collection point:** `LlamaWrapper::generate()` — record when `token_callback` is invoked for the first time.

---

### `llm_per_token_latency_ms` (Histogram)

Per-token generation latency in milliseconds (inter-token interval after the first token).

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | — | Serving model |

**Suggested buckets (ms):** `[1, 5, 10, 25, 50, 100, 250]`

**Collection point:** `LlamaWrapper::generate()` — measure between consecutive `token_callback` invocations.

---

### `llm_tokens_generated_total` (Counter)

Total number of output tokens generated across all requests.

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | — | Serving model |

**Collection point:** `LlamaWrapper::generate()` — increment by `n_tokens` on completion.

---

## 2. Scheduler / Queue Metrics

### `llm_scheduler_queue_length` (Gauge)

Number of requests currently waiting in the continuous batch scheduler queue.

| Label | — | — | No labels; global queue. |
|-------|---|---|---|

**Collection point:** `ContinuousBatchScheduler` — updated on enqueue and dequeue.

---

### `llm_scheduler_preemptions_total` (Counter)

Total number of requests preempted (evicted from active batch back to the queue).

| Label | — | — | No labels. |
|-------|---|---|---|

**Collection point:** `ContinuousBatchScheduler::preempt()`.

---

### `llm_scheduler_rejected_total` (Counter)

Total number of requests rejected due to queue depth limit (backpressure).

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `reason` | string | `queue_full`, `rate_limit`, `quota_exceeded` | Rejection reason |

**Collection point:** `ContinuousBatchScheduler` backpressure path (to be implemented in Q1).

---

### `llm_concurrent_requests` (Gauge)

Number of inference requests currently being processed (in active batch).

| Label | — | — | No labels. |
|-------|---|---|---|

**Collection point:** `ContinuousBatchScheduler` — track active slot count.

---

### `llm_batch_size` (Gauge)

Current continuous batch size (number of sequences in the active batch).

| Label | — | — | No labels. |
|-------|---|---|---|

**Collection point:** `ContinuousBatchScheduler::step()`.

| Label | — | — | No labels (single GPU). Add `device_id` label for multi-GPU. |
|-------|---|---|---|

**Collection point:** `GPUMemoryManager` or `AdaptiveVRAMAllocator` — polled every 10 s.

---

Total GPU VRAM available, in megabytes.

| Label | — | — | As above. |
|-------|---|---|---|

| Label | — | — | No labels. |

**Collection point:** NVML or `nvmlDeviceGetUtilizationRates()` — polled every 10 s.

|-------|---|---|---|

## 4. Model Lifecycle Metrics

### `llm_models_loaded` (Gauge)

Number of models currently loaded into memory (GPU or CPU).

| Label | — | — | No labels. |
|-------|---|---|---|

**Collection point:** `LlamaWrapper` or `MLModelManager` — increment on load, decrement on unload.

---

### `llm_model_memory_mb` (Gauge)

Memory (VRAM or RAM) consumed by a specific loaded model, in megabytes.

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | — | The loaded model |
| `device` | string | `gpu`, `cpu` | Where the model resides |

**Collection point:** `LlamaWrapper::loadModel()` / `unloadModel()`.

---

### `llm_model_load_duration_seconds` (Histogram)

Time to load a model from disk into memory, in seconds.

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `model_id` | string | — | The model being loaded |

**Suggested buckets (s):** `[1, 2, 5, 10, 20, 30, 60, 120]`

**Collection point:** `LlamaWrapper::loadModel()`.

## 6. Error Metrics

### `llm_errors_total` (Counter)

Total errors by type and component.

| Label | Type | Values | Description |
|-------|------|--------|-------------|
| `error_type` | string | `oom`, `timeout`, `grammar_fail`, `gguf_unsupported`, `lora_load_fail`, `context_overflow`, `internal` | Category of error |

## Scrape Configuration

Add the following job to `prometheus.yml` to scrape LLM metrics once the `MetricsServer::start()` HTTP endpoint is implemented (Q1):

```yaml
scrape_configs:
  - job_name: 'themisdb_llm'
    static_configs:
      - targets: ['localhost:9091']
    scrape_interval: 15s
    metrics_path: /metrics
```

## Standard PromQL Queries

### Inference throughput (requests/sec)

```promql
sum(rate(llm_inference_requests_total[5m])) by (model_id)
```

### Token generation rate (tokens/sec)

```promql
sum(rate(llm_tokens_generated_total[5m])) by (model_id)
```

### p99 first-token latency (ms)

```promql
histogram_quantile(0.99, sum by (le, model_id) (rate(llm_first_token_latency_ms_bucket[5m])))
```

### Inference error rate

```promql
sum(rate(llm_inference_failures_total[5m])) by (model_id)
/
sum(rate(llm_inference_requests_total[5m])) by (model_id)
```

### GPU VRAM utilisation

```promql
llm_gpu_memory_used_mb / llm_gpu_memory_total_mb
```

### Response cache hit rate

```promql
sum(rate(llm_cache_hits_total{cache_type="response"}[5m]))
/
(
  sum(rate(llm_cache_hits_total{cache_type="response"}[5m]))
  + sum(rate(llm_cache_misses_total{cache_type="response"}[5m]))
)
```

## Resolved Decisions

The following questions (previously "Open Decisions") have been resolved during Q1–Q4 implementation:

| # | Question | Decision | Resolved |
|---|----------|----------|---------|
| 1 | Should per-token latency use `_ms` or `_seconds`? | `_ms` retained — existing code and dashboards use `_ms`; migration to `_seconds` is a future breaking-change exercise | Q1 |
| 2 | Should `model_id` appear on all metrics or only model-scoped ones? | Model-scoped only (inference, latency, failure, quota metrics carry `model_id`; global counters like `llm_gpu_memory_used_mb` do not) | Q1 |
| 3 | Should queue metrics be per-model or global? | Global — `llm_queue_length` and `llm_backpressure_drops_total` are global counters; per-model breakdown can be added as labels in a future iteration | Q1 |
| 4 | Prometheus scrape interval? | 15 s — configured in `grafana/prometheus.yml` | Q1 |
| 5 | OTel + Prometheus: shared names via bridge, or separate schemas? | Separate — OTel trace context (`trace_id`, `span_id`) propagated on `InferenceRequest`/`InferenceResponse`; Prometheus metrics use this schema unchanged | Q1 |
