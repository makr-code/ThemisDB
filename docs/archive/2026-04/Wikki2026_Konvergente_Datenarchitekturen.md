Convergent Data Architectures for 
Sovereign AI Systems
An Evaluation of ThemisDB in Comparison to Hyperscaler Models
Martin Krüger,*  https://orcid.org/0009-0007-6048-7761
*Correspondence: Martin Krüger, ma.krueger@outlook.com
Abstract. The digitalization of German public administration necessitates AI systems that harmonize high efficiency with strict legal compliance. Prevailing cloud architectures often rely on specialized, distributed databases that suffer from "eventual consistency" (BASE), which is insufficient for legally binding administrative acts. This paper evaluates ThemisDB, a multi-model database system that integrates relational, graph-based, and vector-oriented data under a rigorous ACID transactional framework. Utilizing a local-first approach, the system reduces retrieval latencies to <15ms, demonstrating a significant performance advantage over traditional hyperscaler stacks (120-250ms). A key theoretical contribution of this work is the resolution of the conflict between the probabilistic nature of AI generation (Open World Assumption) and the deterministic requirements of administrative law (Closed World Assumption). Through the implementation of the RAG Judge framework for automated NLI-based quality control and a RAID-sharding mechanism for horizontal scalability, this study proves that sovereign, high-performance, and legally secure AI infrastructures are technically viable for modern government ecosystems.
Keywords: Multi-Model DBMS, Local-First Architecture, Data Sovereignty, Public Administration, Retrieval-Augmented Generation (RAG), ACID Compliance, RAID-sharding, Hallucination Mitigation, AI Governance, Legal Tech
Konvergente Datenarchitekturen für 
souveräne KI-Systeme
Eine Evaluation von ThemisDB im Vergleich zu Hyperscaler-Modellen
Zusammenfassung. Die Digitalisierung der deutschen öffentlichen Verwaltung erfordert KI-Systeme, die hohe Effizienz mit strikter Rechtskonformität vereinen. Gängige Cloud-Architekturen basieren oft auf spezialisierten, verteilten Datenbanken, die unter einer „Eventual Consistency“ (BASE) leiden, was für rechtsverbindliche Verwaltungsakte unzureichend ist. Dieser Beitrag evaluiert ThemisDB, ein Multi-Modell-Datenbanksystem, das relationale, graphbasierte und vektororientierte Daten unter einer strengen ACID-Transaktionsklammer vereint. Durch einen Local-First-Ansatz reduziert das System die Retrieval-Latenzen auf <15ms und demonstriert damit einen signifikanten Performance-Vorteil gegenüber klassischen Hyperscaler-Stacks (120–250ms). Ein zentraler theoretischer Beitrag dieser Arbeit ist die Auflösung des Konflikts zwischen der probabilistischen Natur der KI-Generierung (Open World Assumption) und den deterministischen Anforderungen des Verwaltungsrechts (Closed World Assumption). Durch die Implementierung des RAG Judge Frameworks zur automatisierten NLI-basierten Qualitätskontrolle und eines RAID-sharding-Mechanismus zur horizontalen Skalierbarkeit belegt diese Studie, dass souveräne, hochperformante und rechtssichere KI-Infrastrukturen für moderne staatliche Ökosysteme technisch realisierbar sind.
Stichwörter: Multi-Modell-Datenbank, Local-First Architektur, Datensouveränität, Digitale Verwaltung, RAG-Systeme, ACID-Integrität, RAID-sharding, Halluzinationsprävention, Rechtssichere KI, Öffentliche Verwaltung 4.0.
Einleitung (Introducing)
Die deutsche öffentliche Verwaltung sieht sich mit einem steigenden strukturellen Anpassungsdruck konfrontiert. Faktoren wie der demografische Wandel und der daraus resultierende Wissensverlust durch ausscheidende Fachkräfte erfordern technologische Unterstützungssysteme zur Erhaltung der staatlichen Handlungsfähigkeit. Ohne technologische Unterstützung drohen Ressourcenengpässe sowie wachsende Frustration bei Bürgern und Mitarbeitern. In diesem Kontext ist die Digitalisierung kein optionales Projekt, sondern eine strategische Notwendigkeit. KI-Systeme, insbesondere auf Basis von Retrieval-Augmented-Generation (RAG) [1] [2] [3], bieten die Chance, Verwaltungsprozesse zu transformieren und Mitarbeiter von repetitiven Routineaufgaben wie der Datenerfassung oder der Vollständigkeitsprüfung von Anträgen zu entlasten [4] [5]. Durch diese Entlastung gewinnen die Mitarbeiter Zeit für komplexere, beratungsintensive und persönliche Gespräche mit Bürgern zurück. Diese verbesserten Interaktionen sind entscheidend, um Vertrauen in den öffentlichen Sektor zu schaffen und zu stärken. So wird die KI von einem reinen Effizienzwerkzeug zu einem strategischen Instrument, das die Beziehung zwischen Staat und Gesellschaft nachhaltig festigt und die Leistungsfähigkeit der Demokratie im digitalen Zeitalter unterstreicht, sprichwörtlich zum „Maschinenraum der Demokratie“. Die Grundlage dieses Ansatzes ist eine hybride Architektur, die auf drei sich selbst optimierenden Kreisläufen basiert. Dieser Dreiklang der Prinzipien, namentlich Covina (Daten-Ingestion und Wissenslücken-finden), Clara (kontinuierliche Modellverbesserung) und Veritas (Benutzerinteraktion), adressieren proaktiv die größten Herausforderungen: die Sicherstellung der Datenhoheit, die Gewährleistung faktischer Genauigkeit und die kontinuierliche Anpassung an neue Wissensstände [1]. Es ist darauf ausgelegt, die spezifischen Anforderungen des juristischen Kontextes zu erfüllen, indem es über einfache semantische Vektorsuchen hinausgeht und logisches Multi-Hop-Reasoning [6] über einen Wissensgraphen ermöglicht. Dies erfordert eine Dateninfrastruktur, die nicht nur semantische Ähnlichkeiten findet, sondern auch kausale Zusammenhänge (Graphen) und Metadaten (Relational) transaktional sicher verarbeitet. Die technische Kernanforderung kann hier auch als ein digitaler Zwilling der Verwaltung verstanden werden, der probabilistische KI-Generierung mit der deterministischen Rechtssicherheit von Verwaltungsakten vereint. Die Forschungsfrage dieses Berichts konzentriert sich einerseits darauf, wie eine Datenbankarchitektur, die RAG unter Einhaltung strikter ACID-Garantien ermöglicht und andererseits die probabilistische Natur von Large Language Models (LLMs) mit der für Verwaltungsakte notwendigen deterministischen Rechtssicherheit vereinen kann und ob die Architektur mit den etablierten Lösungen der sog. Hyperscaler (AWS, Google, Meta) mithalten kann. 
Analyse bestehender Paradigmen (Related Work)
Bisherige IT-Strategien folgen dem Industriestandard der sog. „Polyglot Persistence“, wie sie in der UDS3-Architektur [1] umgesetzt wurde. Hierbei kommen spezialisierte Datenbanksysteme (z. B. Neo4j für Graphen, ChromaDB für Vektoren, PostgreSQL für Metadaten) parallel zum Einsatz. Die technische Evaluation dieses Ansatzes offenbart eine fundamentale Schwäche in der Transaktionsintegrität. Da keine globale Transaktionsklammer über physisch getrennte Systeme existiert, können atomare Operationen über Modellgrenzen hinweg nicht garantiert werden. In diesem Architekturmodell weichen strikte ACID-Garantien (Atomicity, Consistency, Isolation, Durability) notwendigerweise dem BASE-Paradigma (Basically Available, Soft state, Eventual consistency). Das Resultat ist eine Inkonsistenz der Daten zwischen „ja“ und „nein“, bei der Datenzustände zwischen den Teilsystemen zeitweise divergieren können. In einem solchen System ist die Datenkonsistenz nicht durch das Datenbanksystem selbst, sondern lediglich durch die Anwendungslogik („Saga-Pattern“) [7] erzwungen, was zu einem Zustand des lediglich „eventuell Korrekten“ führt. In der administrativen Praxis führt dieses Konsistenzmodell zu erheblichen Risiken. Ein konkretes Beispiel ist die Umsetzung von Löschpflichten nach §17 Datenschutzgrundverordnung - DSGVO: Während ein Dokument in der relationalen Aktenführung bereits entfernt wurde, kann es aufgrund der verzögerten Synchronisation im Vektor-Index der KI-Suche weiterhin vorhanden sein.   Für rechtsverbindliche Verwaltungsakte nach §35 Verwaltungsverfahrensgesetz - VwVfG, die eine unumstößliche Tatsachengrundlage erfordern, ist eine solche Architektur unzureichend. Eine KI, die auf inkonsistenten Daten operiert, würde auf Basis faktisch falscher oder veralteter Informationen entscheiden, was die Gerichtsverwertbarkeit des resultierenden Bescheides gefährdet. Theoretisch ließe sich das Konsistenz-Dilemma durch die Definition einer „Single Source of Truth“ (SSOT) innerhalb eines einzigen, generalisierten Datenbanksystems auflösen. Die Analyse verdeutlicht jedoch, dass eine solche Zentralisierung die Fähigkeiten moderner KI-Anwendungen erheblich einschränkt. Spezialisierte Datenbankarchitekturen bewältigen dedizierte Aufgaben – wie die Suche in hochdimensionalen Vektorräumen oder komplexe Graph-Traversierungen – oft wesentlich effektiver als Allzweck-Systeme. Eine erzwungene Vereinheitlichung in einem klassischen System führt dazu, dass die Performance und Skalierbarkeit für KI-Workloads unter das erforderliche Maß sinken, da herkömmliche Indexstrukturen die Komplexität von Vektor-Embeddings nur unzureichend verarbeiten können. Damit resultiert die Wahl eines starren SSOT-Modells oft in einem Kompromiss, bei dem die Datenintegrität durch den Verzicht auf fortgeschrittene analytische Leistungsfähigkeit und Flexibilität erkauft wird. Dieses architektonische Dilemma der Datenpersistenz bildet die direkte Schnittstelle zur logischen Diskrepanz auf der Verarbeitungsebene. Während das RAG den Versuch unternimmt, LLM durch den Abruf verifizierter Fakten zu „erden“, bleibt ein struktureller Konflikt zwischen den zugrundeliegenden Wissensmodellen bestehen: Während die Datenbankebene zur Sicherung der Rechtssicherheit zwingend der Closed World Assumption (CWA) folgen muss – also nur das als wahr anerkennt, was explizit dokumentiert ist –, operieren LLMs nativ nach der Open World Assumption (OWA). Sie interpretieren das Fehlen von Informationen nicht als deren Nichtexistenz, sondern füllen Lücken durch statistische Wahrscheinlichkeiten. Ohne eine technische Brücke, welche die probabilistische Natur der KI in den deterministischen Rahmen der CWA zwingt, bleibt die Integration in rechtssichere Prozesse unmöglich. Die zentrale technologische Herausforderung besteht darin, die beeindruckenden, aber von Natur aus probabilistischen Fähigkeiten moderner Large Language Models (LLMs) in das starre, deterministische Korsett des deutschen Verwaltungsrechts zu integrieren.
Theoretischer Rahmen: Rechtssicherheit in der Verwaltung
Die Auflösung der Diskrepanz zwischen OWA und CWA erfordert eine formale Definition der Wissenssphären innerhalb des Ökosystems. Ein Verwaltungsakt nach § 35 VwVfG – als Regelung eines Einzelfalls mit unmittelbarer Rechtswirkung nach außen – verlangt eine unumstößliche Tatsachengrundlage, was eine strikte Trennung zwischen Vorbereitungs- und Entscheidungsphase notwendig macht. [4] [8] In der Architektur der ThemisDB übernimmt die KI (Vorbereitung) keine hoheitliche Entscheidungsgewalt, sondern fungiert als Assistenzsystem zur Informationsaufbereitung. Um die Güte dieser Vorbereitung sicherzustellen, wird die statistische Wahrscheinlichkeit der KI durch ACID-basiertes Retrieval, die Überwachung von Inferencing-Metriken (TPT/FLARE) und eine NLP-gestützte Semantikprüfung zur präzisen Abbildung rechtlicher Signalverben („muss“, „kann“, „soll“) in einen kontrollierten Rahmen überführt. Ein LLM-as-Judge-Modul [9] validiert zudem Entwürfe gegen fachadministrierte Datensätze, während ein dialektisches Ethik-Modul die Vorbereitung von Ermessensentscheidungen unterstützt. Die finale rechtliche Bewertung und Unterzeichnung verbleiben als Rolle des Menschen (Kontrolle & Entscheidung) exklusiv beim Amtsträger (Human-in-the-Loop). Die Datenbank unterstützt diese Entscheidungshoheit, indem sie die CWA technisch erzwingt: Der Bearbeiter erhält eine faktentreue, zum Zeitpunkt X nachprüfbare Zusammenfassung aller verfügbaren Informationen. Da LLMs von Natur aus probabilistisch agieren, wird ihr Einsatz für vollautomatisierte Prozesse nach § 35a VwVfG kritisch gewürdigt; ThemisDB legt jedoch durch ihre ACID-Garantien den Grundstein für eine deterministische Datenbasis, die über die bei Cloud-Systemen übliche „Eventual Consistency“ (BASE) hinausgeht. Diese theoretische Forderung nach Gerichtsverwertbarkeit führt unmittelbar zu den architektonischen Spezifikationen: Die Notwendigkeit einer nachweisbaren Historisierung wird durch MVCC-Snapshots gelöst, während die kryptografische Unveränderbarkeit der Interaktionskette durch manipulationssichere Audit-Logs gemäß eIDAS-Anforderungen sichergestellt wird.
Die Architektur
Das Fundament bildet die technische Realisierung als konvergente Datenbank - Converged Database (CDB) - einer nativen Multi-Modell-Architektur [10] - die Graph-, Vektor- und relationale Modelle sowie anwendungsspezifische Erweiterungen für Geo-Spatial-Daten, IoT-Zeitreihen und BPMN-Verwaltungsprozesse - um die theoretisch geforderte Closed-World-Assumption physisch durchzusetzen. Die Engine selber wurde dabei in C++20 implementiert, um eine hardwarenahe Programmierung und die Nutzung von Hochleistungsbibliotheken zu ermöglichen. Als transaktionales Storage-Backend dient RocksDB mit seinem LSM (long-structured merge tree) [11], während die Parallelisierung über Intel Threading Building Blocks (TBB) realisiert wird. Ab der Version 1.4 wurde zudem llama.cpp als native Inferenz-Engine direkt in den Kern integriert. Durch diesen monolithischen Aufbau entfallen externe API-Aufrufe und Übersetzungsschichten. Dies ermöglicht u.a. „Zero-time-Pointer-Transfers“, bei denen beispielsweise Ergebnisse einer HNSW-Vektorsuche ohne Serialisierung-Overhead direkt in den Inferenz-Kontext übergeben werden. Der Verzicht auf Netzwerkkommunikation zwischen den Schichten reduziert die Latenz auf das Niveau der Interprozesskommunikation (IPC) im Speicherraum. Die physische Datenhaltung der ThemisDB folgt einem vereinheitlichten Prinzip, bei dem sämtliche logischen Datenmodelle – ob relational, graphbasiert oder vektoriell – auf ein einheitliches Key-Value-Format, die sogenannte Base-Entity, abgebildet werden. Jede Informationseinheit wird dabei als binär-serialisierter Blob im VelocyPack-Format gespeichert. Diese konvergente Struktur ermöglicht ein hocheffizientes Native Pre-Filtering: Indizierte Metadaten können den Suchraum bereits auf Index-Ebene drastisch beschneiden, noch bevor rechenintensive HNSW-Algorithmen für semantische Ähnlichkeitsanalysen herangezogen werden. Um strikte ACID-Garantien und lückenlose Auditierbarkeit zu gewährleisten, operiert die Core-Engine (RocksDB) im Transaction-Mode als Multi-Version Concurrency Control (MVCC) mit Snapshot Isolation. Dieses Verfahren stellt sicher, dass schreibintensive Prozesse, wie die Ingestion neuer Akten über Covina, laufende Leseoperationen oder KI-Analysen zu keinem Zeitpunkt blockieren. Ein wesentliches Merkmal ist die modellübergreifende Atomarität: Ein einziger Commit garantiert die Persistenz aller Teilaspekte einer Entität über relationale Tabellen, Graphen-Kanten und Vektor-Indizes hinweg simultan. Die Gesamtperformance ist dabei maßgeblich vom Write-Ahead-Log (WAL) abhängig. Daten gelten innerhalb der Datenbank erst dann als existent, wenn sie vollständig im Log protokolliert und bestätigt wurden. Ein Teilversagen führt unweigerlich zu einem vollständigen Rollback, wodurch inkonsistente Zustände zwischen den logischen Modellen technologisch ausgeschlossen sind. Jede Einheit wird als binär-serialisierter Blob (VelocyPack) gespeichert (siehe Tabelle 1). Diese Struktur ermöglicht ein hocheffizientes native Vorfiltern: Indizierte Metadaten beschneiden den Suchraum bereits auf Index-Ebene, bevor rechenintensive HNSW-Algorithmen für semantische Ähnlichkeitsanalysen herangezogen werden.

Diese Indexarchitektur erfordert eine Abfragesprache die sowohl die Multi-Modell- als auch die LLM-Fähigkeiten in einem vereint. Um eine klare Abgrenzung zu SQL-basierten zu nicht-SQL Standards zu realisieren haben wir uns für eine Adaption der AQL (ArangoDB query language) entschieden, die zwar hohe Ähnlichkeit zu SQL (für geringe Einstiegshürden) als auch die bereits vorhandenen Multi-modell Fähigkeiten für Relationale und Vektordaten besitzt. Die daraus hervorgehende Advanced Query Language (AQL) erlaubt hybride Abfragen, die räumliche (Geo-Polygone), zeitliche (Zeitreihen) und prozessbewusste (BPMN) Kriterien in einer einzigen Anforderung vereinen. Mittels MVCC-Historisierung ermöglicht AQL zudem „temporale Abfragen“ (Zeitreisen), um den exakten Wissensstand zum Zeitpunkt einer historischen Verwaltungsentscheidung zu rekonstruieren. 
Zur Verdeutlichung des Ansatzes wird im Beispiel (Anlage 1 – AQL.txt) – AQL eine Benutzereingabe zusammen mit einer Datenbankabfrage an ein LLM zur Aufbereitung übergeben: (1) Zunächst wird die Nutzerfrage als numerisches Embedding kodiert, um eine semantische Ähnlichkeitssuche zu ermöglichen – in der AQL-Query wird dies durch `EMBED('text-embedding-3-small', user_query)` ausgedrückt. Die Query-Engine verfügt über einen Kostenoptimierer, der bei der Ausführungsplanung die unterschiedlichen Ressourcenverbräuche der einzelnen Operationen berücksichtigt. Relationale Indexzugriffe werden als sehr kostengünstig modelliert (typischerweise logarithmisch in der Datenmenge), graphenbasierte Traversierungen als mittelmäßig kostspielig (abhängig von Grad und Tiefe des Graphen) und Vektoroperationen sowie LLM-Aufrufe als teuer, da sie entweder externe API-Calls oder GPU-Compute-Ressourcen beanspruchen. Der Optimierer nutzt diese Kostenschätzungen, um eine Ausführungsreihenfolge zu ermitteln, die Operationen mit niedrigen Kosten voranstellt und damit die Eingabemenge für nachfolgende teurere Operationen minimiert. Die Routenfindung arbeitet dabei nach dem Prinzip der „Selectivity Propagation" - Jeder Filterschritt reduziert die Kandidatenmenge für den nächsten Schritt, und die Engine wählt jene Schrittfolge, die den stärksten und kostengünstigsten Filter zuerst anwendet. (2) Vor der rechenintensiven Vektoroperation erfolgt daher eine nach diesem Kostenmodell optimierte Filterung in mehreren Stufen. Relationale Filter selektieren zunächst nach Rechtsgebiet, Themenfeld, Status und Gültigkeitsdatum – entsprechend den `FILTER`-Anweisungen in der AQL für `doc.legal_area`, `doc.topics`, `doc.status` und `doc.valid_until`. Diese Operationen sind kostengünstig und reduzieren die angenommene Datenmenge um 80–95 Prozent. (3) Graphenbasierte Filter schränken sodann ein: In der AQL werden die zugriffsberechtigten Regionen des Nutzers durch `FOR v IN 0..2 OUTBOUND CONCAT('users/', @user_id) region_access` ermittelt und danach wird mit `FILTER doc.region IN allowed_regions` überprüft, welche Dokumente dem Nutzer tatsächlich zugänglich sind. Diese Graphtraversierung ist teurer als ein einfacher Feldvergleich, aber die Engine führt sie durch, nachdem bereits relationale Filter eine kleinere Menge isoliert haben. Die Kombination dieser Filter stellt sicher, dass nur für die jeweilige Organisation und den Nutzer tatsächlich relevante Dokumente in den nächsten Schritt gelangen. (4) Erst nach diesen Vorfiltern wird die rechenintensive Embedding-Ähnlichkeit berechnet – dass `COSINE_SIMILARITY(doc.embedding, q_emb)` wird somit nur auf einer drastisch reduzierten Menge angewendet. Die relevantesten Dokumente werden anhand ihrer strukturierten Metadaten und ihrer im Graphmodell hinterlegten Berechtigungen aufbereitet. (5) Die finalen Kontextinformationen – Titel, Inhaltsauszug – werden in der AQL durch `CONCAT(doc.title, "\n", SUBSTRING(doc.content, 0, 200))` konstruiert. Diese Kontextinformationen dienen als Input an das Sprachmodell (`PROMPT('gpt-4', ...)`), das damit nicht nur Dokumentinhalte, sondern auch Zugriffsberechtigung in seiner Antwort berücksichtigen kann. Die Abfragepipeline vereinigt relationale, dokumenten-, vektor- und graphenbasierte Operationen in einer durchgängigen Ausführung innerhalb einer einzigen AQL-Query. Dadurch bleibt die gesamte Kette für den Anwender in einer einheitlichen Sprache formulierbar und steuerbar. Die Kosten pro Anfrage werden je Verarbeitungsschritt erfasst und dem entsprechenden Rechenaufwand zugeordnet. Durch diese Integration können komplexe Verwaltungskontexte – Zuständigkeiten, regionale Hierarchien, differenzierte Zugriffsmodelle – nahtlos in die daten- und KI-gestützte Antwortfindung einbezogen werden, ohne dabei unnötige KI-Ressourcen zu verbrauchen. Ein Kernmerkmal der Version 1.5.x ist das integrierte Training und Management interner und externer LoRA-Adapter (Low-Rank Adaptation). Diese werden kontinuierlich mit anonymisierten Verwaltungsentscheidungen trainiert, über das Auto-Binding-System dynamisch geladen und über Sharding-Mechanismen im Cluster verteilt. Dies ermöglicht eine präzise Ausrichtung auf juristische Fachsprache und reduziert die Halluzinationsrate signifikant. Auch bleibt der fachspezifische Adapter in Bezug auf Training und Verteilung in der Hoheit der jeweiligen Behörde und kann durch fachspezifische LLM-as-jugde gegen die „golden Dataset“ geprüft werden bevor sie im Cluster verteilt werden.Auch die System-prompts sind nicht zwingend hard-codiert, sondern entwickeln sich von einer Basis-Implementierung (dezeit als YAML implementiert) weiter. Dabei kommen Iterative Optimierung: Basierend auf Forschungsergebnissen von DSPy und AutoPrompt nutzt das System einen iterativen Optimierer, der Prompts durch automatische Metriken (z. B. Jaccard-Ähnlichkeit, Levenshtein-Distanz) bewertet und verfeinert [12] [13]. Few-Shot-Selektion [14]: Ein intelligenter Selektor wählt aus der Datenbank die am besten geeignete Beispiele (Few-Shots) aus, um das Modell im Kontext des spezifischen Einzelfalls zu "erden". Dies geschieht durch Greedy-Optimierung zur Sicherstellung der semantischen Diversität und Meta-Prompting [15]: Das System generiert mittels Meta-Prompts Verbesserungsvorschläge für Instruktionen, falls die Evaluation eine zu hohe Varianz in den KI-Antworten identifiziert, zum Einsatz. Eine Evaluation des Moduls der Prompt-Verbesserung steht noch aus.
Die DB erfüllt die BSI-Anforderungen durch mehrere integrierte Sicherheitsmechanismen. Die Plattform nutzt Apache Ranger zur zentralisierten Zugriffskontrolle und implementiert feldspezifische AES-256-GCM-Verschlüsselung mit HSM-Anbindung (z.B. Thales Luna HSM), um sensible Daten bereits bei der Speicherung zu schützen. Die Gerichtsverwertbarkeit wird durch ein revisionssicheres Audit-Log gewährleistet, das auf kryptografischen Hash-Chains basiert. Jeder Audit-Eintrag enthält einen SHA-256-Hash des vorherigen Eintrags, wodurch nachträgliche Manipulationen mathematisch sofort erkannt werden. Dies wird durch digitale RFC 3161-konforme Zeitstempel gemäß eIDAS-Standard ergänzt, die für elektronische Signaturen erforderlich sind. Die mTLS-basierte Zero-Trust-Kommunikation zwischen allen Systemkomponenten gewährleistet eine lückenlose Authentifizierung und Verschlüsselung aller Datentransporte. Das System differenziert zwischen vier Klassifizierungsstufen für Daten: öffentlich, VS - nur für Dienstgebrauch, Geheim und Streng-Geheim. Die Verschlüsselung wird je nach Klassifizierungsstufe angepasst – bei höchster Einstufung werden HSM-gestützte Verfahren verwendet. Dies betrifft nicht nur Dokumente und Dateien (die auf Dateisystemebene verschlüsselt werden), sondern auch strukturierte relationale, Vektor- und Graph-Daten im Ruhezustand. Es implementiert Mechanismen wie Memory-Locking und sichere Speicherbereinigung, verlässt sich aber vollständig auf das Betriebssystem und die Hardware für die eigentliche Speicherzugriffskontrolle. Daten werden im Speicher nur zur Verarbeitung entschlüsselt und durch Betriebssystem-Isolation (getrennte Prozesse) sowie Kernel-Mechanismen wie ASLR, DEP und Paging-Schutz geschützt. Eine granulare Zugriffskontrolle unterhalb von Page-Ebene ist auf modernen Prozessoren nicht möglich. Die Multi-Version Concurrency Control (MVCC) ermöglicht zudem zeitpunktgenaue Abfragen beliebiger Datenpunkte. Dies bedeutet, dass jeder Datenzustand chronologisch rekonstruierbar ist – ein Bruch der Hash-Chain in den Audit-Logs würde damit unweigerlich erkannt. Insgesamt sichert ThemisDB Daten sowohl im Ruhezustand als auch in der Übertragung nach technischem Stand-der-Technik und mit kryptografischen Methoden auf Zeilenebene. 
Um die physischen Kapazitätsgrenzen einzelner Datenbank-Knoten zu überwinden und die für den staatlichen Sektor unabdingbare Hochverfügbarkeit zu gewährleisten, implementiert die ThemisDB ein spezialisiertes RAID-sharding-Verfahren. Dieser architektonische Ansatz transferiert bewährte Redundanzkonzepte der klassischen Speichertechnik (Festplatten-RAID) in die Welt verteilter Datenbanken, indem er ein hash-basiertes Sharding mit variablen Redundanzstrategien verknüpft. Die Datenverteilung erfolgt dabei deterministisch über einen Consistent Hash Ring, was eine effiziente Adressierung der Shards ermöglicht und die Grundlage für ein belastbares Replica-Management bildet. Je nach spezifischer Anforderung an die Datenintegrität oder die Abfragegeschwindigkeit unterstützt das System unterschiedliche Betriebsmodi: Während RAID 0 durch paralleles Striping den Durchsatz maximiert, bieten RAID 1 und RAID 10 durch Mirroring-Verfahren eine vollständige Replikation, die selbst bei Ausfällen mehrerer Knoten eine starke Konsistenz (Strong Consistency) mittels Two-Phase-Commit garantiert. Für speichereffiziente Szenarien kommt zudem RAID 5 zum Einsatz, das mittels Erasure Coding und XOR-Paritätsberechnungen einen robusten Ausfallschutz bei minimiertem Overhead realisiert. Eine Besonderheit stellt die GEO_MIRROR-Strategie dar, welche eine geografische Datenverteilung ermöglicht, um regionale Ausfallszenarien abzusichern und die Souveränität über den physischen Datenstandort zu wahren. Die interne Kommunikation innerhalb dieses Clusters wird durch mTLS-Verschlüsselung und zertifikatsbasierte Authentifizierung nach modernen Zero-Trust-Prinzipien abgesichert. In ersten Laboruntersuchungen innerhalb einer Docker-basierten Orchestrierung konnte durch automatisiertes Failover und intelligentes Read Preference Routing nachgewiesen werden, dass die Architektur auch unter Last stabil bleibt. Die Koordination der Knoten erfolgt dabei über einen Raft-Konsens-Algorithmus, der sicherstellt, dass das Gesamtsystem auch bei Netzwerkpartitionierungen einen konsistenten Zustand beibehält. Obwohl eine abschließende Validierung in einer behördenübergreifenden Realumgebung noch aussteht, belegen die bisherigen Ergebnisse, dass der Local-First-Ansatz der ThemisDB durch das RAID-sharding erfolgreich in eine horizontal skalierbare Infrastruktur überführt werden kann, ohne die rechtssicheren ACID-Garantien aufzugeben.
Methodik (Methods)
Die Evaluierung verfolgt eine vierdimensionale Zielsetzung: Die methodische Validierung der Entwicklungszyklen, die technische Leistungsprüfung, die funktionale Optimierung des LLM-Inferencing sowie die Verifikation der ethisch-rechtlichen Validität der Ausgaben. Die Systementwicklung folgt einem iterativen „Closed-Loop“-Prozess, der durch spezialisierte Entwickler-KIs wie Anthropic Claude 4.5 oder OpenAI GPT 5.2 Codex unterstützt wird. Bis zum Erreichen der Version 1.0 lag der Schwerpunkt der Entwicklung auf der Konsolidierung der Core-Engine. Im Fokus standen dabei insbesondere die Integration des Base-Entity-Modells in RocksDB sowie die Sicherstellung ACID-konformer CRUD-Operationen. Jeder Entwicklungsschritt wird durch die Erstellung eines Pflichtenheftes eingeleitet. Dieses definiert verbindlich, in welchem Rahmen eine zu implementierende Funktion welche Aufgaben zu erfüllen hat. Auf dieser Basis generiert die KI den erforderlichen Sourcecode (Boilerplate) sowie die dazugehörigen Unit-Tests. Nach dem erfolgreichen Kompilieren des Quellcodes wird die Funktion anhand dieser Tests validiert und bei Bedarf gedebuggt. Der gesamte Prozess wird kontinuierlich durch den Entwickler gesteuert und geprüft. Dabei folgt die Architekturplanung dem Top-Down-Prinzip – von der Struktur (Namespaces, Klassen) hin zum Detail (Einzelfunktionen) –, während die Validierung in umgekehrter Reihenfolge (Bottom-Up) erfolgt. Pflichtenheft und Lieferantendokumentation bilden hier die prüfbare Qualitätskontrolle.
Die Leistungsmessung erfolgt gemäß ISO/IEC 14756:2015 auf einer dedizierten Referenz-Hardware, um OS-Interferenzen zu minimieren: CPU: Intel Core i9-12900K (20 Kerne, 3,7 GHz). RAM/Disk: 64 GB DDR5-RAM; 2 TB NVMe PCIe 4.0 SSD. Umgebung: Windows x64, MSVC 14.44, Release-Build (-O3). Die CHIMERA Suite nutzt zur Validierung die Standards YCSB (Skalierbarkeit), TPC-C/H (Integrität/Join-Performance) und ANN-Benchmarks (Vektorsuche). 
Die Ermittlung der Halluzinationsrate ist dem Stand der Technik nach einem probaten Mittel, um die Leistungsfähigkeit des Retrievals einer RAG-Architektur zu verifizieren. Die faktische Integrität der KI-Antworten wird über den Knowledge Gap Detector (Phase 2-Implementierung) mittels Token-Probability-Tracking (TPT) bestimmt. Dabei wird die Perplexity während der Generierung kontinuierlich überwacht. Das System berechnet einen Confidence Score aus den Token-Wahrscheinlichkeiten mittels geometrischer Mittel. Fällt die Konfidenz unter 70% (confidence_threshold = 0.7), wird eine Wissenslücke erkannt und eine erweiterte Dokumentensuche ausgelöst. Parallel dazu wird die Perplexity in einem Sliding Window von 10 Tokens (perplexity_window_size = 10) überwacht. Überschreitet die Perplexity den Schwellenwert von 100.0 (perplexity_threshold), triggert dies eine Multi-Hop-Retrieval-Strategie zur Beschaffung zusätzlicher Kontextinformationen. Vor der Konfidenzberechnung werden Ausreißer-Token mittels Z-Score-Filterung (zscore_threshold = 3.0) entfernt, um robuste Metriken zu gewährleisten und Standardabweichungen zu glätten. Das FLARE-Verfahren (Forward-Looking Active REtrieval) arbeitet iterativ in bis zu 3 Retrieval-Runden (max_retrieval_rounds = 3). Wenn die Query-Coverage unter 80% (coverage_threshold = 0.8) liegt, werden fehlende Aspekte identifiziert und die Suchanfrage dynamisch neu formuliert. Neue Dokumente werden abgerufen und dedupliziert zum bestehenden Kontext hinzugefügt. Bei Konfidenz unter 50% (flare_confidence_threshold = 0.5) wird das Re-Retrieval aktiv. Diese Metriken lassen sich während der Inferenz zählen und geben präzisen Aufschluss darüber, wie oft der Generierungsprozess unterbrochen werden musste, aus welcher Quelle Wissenslücken stammen (Retrieval-Fehler, unzureichende Dokumentenabdeckung, veraltete Informationen) und welche Retrieval-Strategie erfolgreich war (Expand Search, Multi-Hop, Query Reformulation). Die gesammelten Halluzinationsmetriken fließen in drei Verbesserungsschleifen ein: Erstens werden identifizierte Wissenslücken-Muster zur Prompt-Optimierung genutzt. Zweitens dienen Coverage- und Similarity-Scores zur Optimierung der Embedding-Strategien und Indexierungsparameter beim Retrieval-Tuning. Drittens werden über die ThemisHelpLoRA-Komponente Halluzinations-Feedback und Korrekturen in Trainings-Batches (feedback_batch_size = 100) gesammelt und zur inkrementellen Adapter-Verbesserung genutzt. Bei Unterschreitung der Genauigkeitsschwelle von 80% (min_accuracy_threshold) erfolgt ein automatisches Rollback. Zusätzlich werden 5 Samples (self_consistency_samples = 5) mit variierenden Temperaturen (0.7, 0.8, 0.9) generiert und auf semantische Konsistenz geprüft. Ein Consistency-Score unter 60% (consistency_threshold = 0.6) indiziert widersprüchliche Informationen und triggert eine Claim-Verifikation gegen die Quelldokumente.
Ergebnisse (Results)
Obwohl die Lösungen der Hyperscaler eine hohe horizontale Skalierbarkeit bieten, scheitern sie oft an den spezifischen Anforderungen des deutschen Verwaltungsrechts. Die "funktionale Parität" zu Hyperscalern wird insbesondere durch den "Local-First"-Ansatz und die Integration BSI-konformer Sicherheitsmodule erreicht. Es konnte schlüssig gezeigt werden, dass die bei Hyperscalern übliche Trennung von Graph-DB (z. B. AWS Neptune), Vektor-DB (z. B. Pinecone/Chroma) und relationaler DB (z. B. Aurora) eine "Inkonsistenzfalle" darstellt, die für hoheitliche Entscheidungen inakzeptabel ist. Weiterhin konnte gezeigt werden das eine MMDB technisch machbar ist und mindestens vergleichbare Performance bieten kann. Die quantitative Evaluation der ThemisDB-Architektur im Vergleich zu cloud-basierten RAG-Systemen (z. B. AWS Bedrock mit Pinecone) zeigt teils signifikante Performance-Vorteile durch den Local-First-Ansatz. In standardisierten Testszenarien konnten die Netzwerk-Hops durch die In-Process-Integration der Vektor-Engine eliminiert werden. Während verteilte Systeme eine durchschnittliche Retrieval-Latenz von 120ms bis 250ms aufweisen, reduziert ThemisDB diesen Wert auf unter 15ms. Dies ist besonders kritisch für die Echtzeit-Validierung von Verwaltungsakten, bei denen die Latenz der LLM-Inferenz bereits einen signifikanten Zeitanteil beansprucht. Die Messungen zeigen eine signifikante Steigerung von v1.0.0 zu v1.4.0, insbesondere durch die Schließung des „Parallel Scaling Gap“ mit Hilfe der Intel TBB.

Ein zentrales Ergebnis der Untersuchung ist die erfolgreiche Auflösung des Konflikts zwischen der probabilistischen Natur der Transformer-Modelle (Open World Assumption) und der deterministischen Rechtssicherheit der Verwaltungsdatenbank (Closed World Assumption). Dabei fungiert die DB hierbei als Ankerpunkt: Während das LLM-Hypothesen generiert, stellt die integrierte ACID-Klammer sicher, dass nur Fakten, die innerhalb der geschlossenen Datenbankwelt verifiziert wurden, in den finalen Verwaltungsakt einfließen. Dieser duale Ansatz ermöglicht es, die Innovationskraft generativer KI mit der notwendigen Beweissicherheit (eIDAS-Konformität) zu vereinbaren.
Um systembedingte Halluzinationen zu minimieren, nutzt die Evaluation die Multi-Modell-Struktur der ThemisDB zur Cross-Validierung. Durch die Verknüpfung von Graph-Logik (relationale Abhängigkeiten) und Vektor-Suche (semantische Ähnlichkeit) wird der LLM-Output gegen die strikte Schema-Integrität der Datenbank geprüft. Ergebnisse zeigen, dass Fehlinterpretationen des Modells durch automatische Integritäts-Checks auf Datenbankebene erkannt und markiert werden können. Dies stellt einen entscheidenden Fortschritt gegenüber reinen Vektor-Datenbanken dar, denen die relationale Kontrollschicht fehlt. Dabei liefert die Evaluation des Ethik-Moduls und des rechtlichen Rahmens (§ 35/35a VwVfG) auch erste Erkenntnisse zur Rechtssicherheit bei der Vorbereitung von Ermessensentscheidungen.
Während die Skalierbarkeit des monolithischen Kerns initial als Risiko identifiziert wurde, zeigt die Analyse des RAID-sharding, dass die Trennung von lokaler Rechenlast (In-Process) und globaler Datenverfügbarkeit (Shared-Nothing-Architektur der Shards) ein resilientes Wachstum ermöglicht. Die Komplexität verschiebt sich hierbei von der Datenbank-Engine hin zur Orchestrierung der Shards, was durch automatisierte Key-Management-Systeme (HSM-Integration) aufgefangen wird. Dabei offenbart die Evaluation der Architektur ein Spannungsfeld zwischen der erreichten Performance-Steigerung und den Anforderungen an die Systemwartung.
Optimierungspotenziale und Skalierbarkeit: Während die In-Process-Integration (Local-First) die Netzwerk-Latenz auf ein Minimum reduziert (siehe 6.1), zeigt die Analyse der monolithischen Struktur deutliche Grenzen bei der horizontalen Skalierbarkeit. Für zukünftige Iterationen im VCC-Ökosystem ist eine Optimierung der Speicherverwaltung für extrem große Vektor-Indizes (Multi-Terabyte-Bereich) erforderlich. Hier bietet der Übergang zu einer hybriden Cloud-Edge-Synchronisation Potenzial, um die lokale Souveränität mit der Skalierbarkeit zentralisierter Ressourcen zu koppeln, ohne die ACID-Garantien zu verletzen.
Sicherheitsrisiken und Komplexität: Ein identifiziertes Risiko liegt in der erhöhten Wartungskomplexität, die aus der Konvergenz unterschiedlicher Datenmodelle (Graph, Vektor, Relational) resultiert. Die BSI-konforme Absicherung über die kryptografische Hash-Chain (Audit-System) stellt zwar die Beweissicherheit sicher, erfordert jedoch spezialisiertes Personal für die Schlüsselverwaltung (HSM/PKCS#11). Ein systemimmanentes Risiko bleibt zudem die ‚Open World‘-Problematik der LLMs: Trotz strikter Datenbankintegrität können fehlerhafte Modell-Inferenzen die Rechtssicherheit gefährden, sofern keine automatisierte Cross-Validierung gegen die ‚Closed World‘ der relationalen Fakten erfolgt. Die Resilienz des Gesamtsystems hängt somit maßgeblich von der korrekten Konfiguration der Validierungsschichten ab.
Um die Validierung der LLM-Outputs über die rein relationale Ebene hinaus zu systematisieren, wurde das Framework ‚RAG Judge‘ als integraler Bestandteil der ThemisDB-Architektur konzipiert. Kernstück ist eine Quality Control Pipeline (QC), die eine automatisierte Bewertung der generierten Antworten in Echtzeit vornimmt. Hierbei kommt ein NLIFaithfulnessVerifier zum Einsatz, der mittels Natural Language Inference (NLI) prüft, ob die Behauptungen des LLM (Hypothesis) logisch aus den Datenbank-Fakten (Premise) folgen (Entailment) oder im Widerspruch dazu stehen (Contradiction). Durch die direkte Anbindung an die InferenceEngineEnhanced wird ein Performance-Target von <500ms für den gesamten Validierungsprozess angestrebt. Obwohl dieser Prozess aktuell in einer Laborumgebung evaluiert wird, zeigen die ersten Integrationstests, dass die Kombination aus deterministischen Integritäts-Checks und probabilistischer NLI-Verifikation die verbleibende Halluzinationsrate signifikant senkt. Damit wird die diskutierte Cross-Validierung technisch operationalisiert.
Fazit (Conclusion)
Die vorliegende Evaluation zeigt, dass ThemisDB als konvergente Datenarchitektur die technischen und rechtlichen Anforderungen an eine souveräne KI in der Verwaltung erfüllt. Es wurde nachgewiesen, dass der Local-First-Ansatz nicht nur ein Souveränitätsgewinn ist, sondern durch die Eliminierung von Netzwerk-Hops eine überlegene Performance bietet, die für die Echtzeit-Validierung von Verwaltungsakten essenziell ist. Die Einführung von RAID-sharding entkräftet die Bedenken hinsichtlich der Skalierbarkeit monolithischer Systeme und ermöglicht den Einsatz in großskaligen Szenarien. Mit dem RAG Judge Framework wurde zudem eine technologische Antwort auf das Problem der Halluzinationen geliefert: Die Kombination aus relationaler Integrität und NLI-basierter Glaubwürdigkeitsprüfung (Natural Language Inference) schafft das notwendige Vertrauen in die KI-gestützte Entscheidungsvorbereitung (§ 35/35a VwVfG). Ein entscheidendes Ergebnis dieser Evaluation ist die technologische Kausalität zwischen Systemperformance und Rechtssicherheit: Die gemessene Reduktion der Retrieval-Latenz auf <15ms durch den Local-First-Ansatz ist kein rein quantitativer Selbstzweck. Sie bildet vielmehr die notwendige infrastrukturelle Voraussetzung, um komplexe Validierungsschichten wie das RAG Judge Framework überhaupt erst in Echtzeit-Szenarien zu operationalisieren. Erst durch diesen Zeitgewinn auf Datenbankebene verbleibt innerhalb des angestrebten Antwortzeitfensters von <500ms ausreichend Spielraum für die NLI-basierte Cross-Validierung gegen die Closed World Assumption der Verwaltungsdaten. Damit wird bewiesen, dass eine souveräne, lokale Architektur der Cloud-Konkurrenz nicht nur in puncto Datenschutz überlegen ist, sondern die für automatisierte Verwaltungsakte (§ 35a VwVfG) kritische Verbindung von Geschwindigkeit und Fakten-Integrität erst ermöglicht.
Ausblick: Zukünftige Arbeiten werden sich auf die weitere Automatisierung der Modell-Ladezyklen sowie die BSI-Zertifizierung der kryptografischen Hash-Chains konzentrieren. Ziel bleibt die vollständige technische Suzeränität der deutschen Verwaltung bei der Nutzung generativer KI-Technologien.

Anlage 1 – AQL.txt: Vollständige RAG-Pipeline-Abfrage (ThemisDB AQL)

Die folgende AQL-Abfrage implementiert den im Abschnitt 4 (Architektur) beschriebenen 5-Schritt-Prozess: Embedding-Kodierung der Nutzeranfrage, relationale Vorfilterung, graphbasierter Berechtigungs-Filter, Vektor-Ähnlichkeitsberechnung und LLM-Prompt-Generierung. Der vollständige kommentierte Quelltext ist in der Datei Anlage_1_AQL.txt (beiliegend) enthalten.

```aql
// Bindungsparameter:
//   @user_query  – Nutzerfrage (String)
//   @user_id     – Kennung des Sachbearbeiters (String)
//   @legal_area  – Rechtsgebiet, z. B. "BauordnungsR" (String)
//   @topics      – Themenfelder (Array of String)

// Schritt 1: Embedding-Kodierung der Nutzeranfrage
LET q_emb = EMBED('text-embedding-3-small', @user_query)

// Schritt 3 (Vorbereitung): Erlaubte Regionen via Graph-Traversierung
LET allowed_regions = (
    FOR v IN 0..2 OUTBOUND CONCAT('users/', @user_id) region_access
        RETURN v._id
)

// Schritte 2–4: Kostenoptimierte Filterung + Vektor-Ranking
LET ranked_docs = (
    FOR doc IN documents
        FILTER doc.legal_area  == @legal_area          // relational (günstig)
        FILTER @topics         ALL IN doc.topics        // relational (günstig)
        FILTER doc.status      == 'active'              // relational (günstig)
        FILTER doc.valid_until >= DATE_NOW()            // relational (günstig)
        FILTER doc.region      IN allowed_regions       // graph     (mittelmäßig)
        LET sim = COSINE_SIMILARITY(doc.embedding, q_emb)  // vektor (teuer)
        FILTER sim >= 0.70
        SORT sim DESC
        LIMIT 50
        RETURN { title:      doc.title,
                 context:    CONCAT(doc.title, "\n", SUBSTRING(doc.content, 0, 200)),
                 similarity: sim }
)

// Schritt 5: Kontext-Aufbereitung und LLM-Prompt
LET context_str = CONCAT_SEPARATOR("\n---\n", ranked_docs[*].context)

RETURN PROMPT('gpt-4',
    CONCAT('Beantworte die folgende Frage auf Basis der Dokumente:\n\n',
           context_str, '\n\nFrage: ', @user_query),
    { max_tokens: 512, temperature: 0.1 })
```
