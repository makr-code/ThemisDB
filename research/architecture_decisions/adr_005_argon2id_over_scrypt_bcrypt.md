# ADR-005: Argon2id over scrypt / bcrypt for Key Derivation

**Status:** Accepted  
**Date:** 2023-04-01  
**Deciders:** @themisdb-core-team  
**Modules Affected:** `plugins/user_storage_encrypted/`  
**Related Research:** [Argon2id KDF Best Practices](../best_practices/argon2id_kdf.md)

---

## Context

The `user_storage_encrypted` plugin stores per-user data encrypted at rest. Encryption keys are derived from a user-supplied passphrase using a Key Derivation Function (KDF). The derived key is never stored — it is re-derived on each unlock.

Requirements at decision time:

- **Memory-hard:** The KDF must require a significant amount of RAM per invocation to defeat GPU/ASIC parallel brute-force attacks (≥ 64 MB working memory).
- **Time-tunable:** The iteration/time cost must be adjustable to target 0.5–1.0 s on target hardware (commodity server CPU) to rate-limit online attacks.
- **Side-channel resistance:** The KDF should not leak secret information via cache-timing attacks in the memory-access pattern (important for shared-cloud environments).
- **Standard compliance:** Must be recommended by a current IETF or NIST standard, or OWASP Password Storage Cheat Sheet, for auditability.
- **C++ integration:** Must have a C or C++ library available via vcpkg with an Apache 2.0 or MIT license.

## Decision Drivers

- **GPU/ASIC resistance:** Memory-hard KDF requiring ≥ 64 MB RAM per invocation to defeat parallel attacks on commodity GPUs.
- **Side-channel resistance:** Access pattern during derivation must not be trivially exploitable via cache-timing (Argon2i mode).
- **OWASP / RFC compliance:** Recommended by OWASP Password Storage Cheat Sheet 2023 and RFC 9106 as first choice for new systems.
- **Time cost tunability:** Parameters must be adjustable without re-encrypting stored data (salt + params stored alongside ciphertext).
- **Password length independence:** Must not truncate passwords (bcrypt 72-byte limit is a hard rejection criterion).

## Considered Options

| Option | Pros | Cons |
|--------|------|------|
| **Argon2id (RFC 9106)** | PHC winner (2015); combines side-channel resistance (Argon2i) and GPU resistance (Argon2d); OWASP first recommendation; RFC 9106 standardized; memory-hard; no password-length limit; libsodium + standalone C reference implementation | Relatively newer (2015 vs. 1999 for bcrypt); requires tuning for target hardware |
| **bcrypt (Niels Provos, 1999)** | Widely deployed; well-understood; blowfish-based | 72-byte password truncation (security hazard for long passphrases); fixed 4 KB memory cost — not memory-hard (trivially GPU-parallelizable in 2023); OWASP lists as acceptable only for legacy systems |
| **scrypt (Percival, 2009)** | Memory-hard; RFC 7914; stronger than bcrypt | Parameters (N, r, p) interact in non-obvious ways; sequential memory access pattern is not side-channel resistant; no side-channel-safe variant; libsodium support but less ergonomic API |
| **PBKDF2 (RFC 2898)** | NIST-approved; FIPS 140-2 compliant; simple | Not memory-hard — GPU can evaluate millions of PBKDF2 iterations in parallel; OWASP recommends only where FIPS compliance mandates it; unsuitable for passphrase-to-key derivation in 2023 |

## Decision

**Chosen: Argon2id via libsodium (`crypto_pwhash`)**

Argon2id is the hybrid variant combining:

- **Argon2i passes** for the first half of the computation — data-independent memory access patterns resist side-channel attacks in shared environments.
- **Argon2d passes** for the second half — data-dependent access patterns maximize GPU/ASIC brute-force cost.

This hybrid makes Argon2id strictly superior to pure Argon2i or Argon2d for passphrase-to-key derivation when both side-channel resistance and GPU resistance are required.

**Production parameters adopted** (per OWASP 2023 and RFC 9106 §4 recommendations, tuned to ≤ 1 s on an AMD EPYC 7443 single core):

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `m` (memory) | 65 536 KiB (64 MB) | Minimum recommended by RFC 9106 for interactive login |
| `t` (iterations) | 3 | Measured 850 ms on target hardware; RFC 9106 minimum for Argon2id |
| `p` (parallelism) | 4 | Matches ThemisDB server default thread count; `crypto_pwhash` uses all lanes |
| Salt length | 32 bytes | Generated by `randombytes_buf()` per derivation |
| Output length | 32 bytes | AES-256 key |

Implementation: `libsodium`'s `crypto_pwhash()` wraps Argon2id with safe defaults and handles platform endianness, alignment, and zeroization of intermediate buffers via `sodium_memzero()`.

bcrypt was rejected because its 72-byte password truncation is a hard security failure mode — a user passphrase longer than 72 bytes silently reduces to the 72-byte prefix, creating a weaker-than-intended key. PBKDF2 was rejected because it is not memory-hard and is trivially accelerated by GPU clusters.

## Consequences

### Positive
- 64 MB × 3-pass Argon2id raises the cost of offline brute-force on a 2023 GPU (RTX 4090) to < 2 derivations/sec, compared to > 1 000 bcrypt hashes/sec.
- RFC 9106 standardization provides a clear reference for security audits and compliance documentation.
- libsodium's `crypto_pwhash` API handles secure memory zeroing, misuse-resistant parameter validation, and output encoding — reducing implementation error surface.
- Parameters are stored alongside the salt in the encrypted file header (Argon2id encoded string format), enabling future parameter upgrades without re-encrypting data.

### Negative / Trade-offs
- **0.85 s derivation time** adds perceptible latency on first unlock. *Accepted because: this is intentional — the cost deters brute-force; interactive UX guidance recommends showing a progress indicator.*
- **64 MB RAM spike per unlock:** In a multi-user server context, simultaneous unlocks could briefly spike memory by N × 64 MB. *Mitigation: a `KdfThrottle` semaphore in `plugins/user_storage_encrypted/` limits concurrent derivations to 4.*
- **libsodium dependency:** Adds a new vcpkg dependency. *Accepted because: libsodium is a well-audited, widely deployed cryptographic library with no known vulnerabilities; the security benefit justifies the dependency.*

### Neutral
- Argon2id parameters can be increased in future releases; files encrypted with old parameters are re-keyed on next password change (opt-in migration path).
- The `IKdf` interface in `plugins/user_storage_encrypted/kdf.hpp` abstracts the KDF, allowing test injection of a fast mock KDF (`t=1, m=1024`) without changing production code.

## Validation

- [x] Argon2id derivation time measured: 850 ms on AMD EPYC 7443 single core with `m=65536, t=3, p=4`
- [x] GPU resistance verified: RTX 4090 achieves < 2 derivations/sec (measured via hashcat benchmark)
- [x] Salt uniqueness verified: each derivation produces unique output with unique salt (unit test)
- [x] libsodium `crypto_pwhash` integration test: encrypt → unlock → verify key identity
- [x] `KdfThrottle` semaphore integration test: 8 concurrent unlock requests complete without OOM
- [ ] Security audit of `plugins/user_storage_encrypted/` KDF integration (pending external review)
- [ ] Parameter upgrade migration test: old-param file re-keyed on password change
